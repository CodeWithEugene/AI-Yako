# AI Yako. Build Plan (Yako)

> **Scope.** The complete, end-to-end plan to design, build, harden, and ship Yako, the offline English-Swahili translator, to a position 1 standard.
> **Constraint set.** Solo builder. One Apple Silicon Mac (arm64, 16 GB RAM, macOS 27, Node 26, npm 11). About 3 days. No physical phone. Goal is to win, not just to finish.
> **Reads with.** `docs/4.solution.md` (the decision). This document is the "how" to its "what."

This is written the way a strong product org would run the build. It covers product definition, experience design, system architecture, code quality, the AI pipeline, performance, privacy, security, accessibility, internationalization, offline behavior, testing, observability, the demo, video production, packaging, documentation, submission, and the risks and roadmap around all of it.

---

## Part 1. Product definition

### 1.1 Elevator pitch

Yako is a translator that lives entirely on your device. It hears English and Swahili, translates between them, and speaks back, with the internet switched off. No account, no API key, no cloud, no cost per use. Your words never leave your device because they never have to.

### 1.2 The one thing it must do better than anything

Hold a real, two-way, spoken English-Swahili exchange in airplane mode, fast enough to feel like a conversation, on hardware a normal person owns. Every decision is subordinate to that.

### 1.3 Jobs to be done

- A market trader who speaks Swahili needs to understand an English-speaking customer right now, with no data bundle.
- A nurse needs to explain dosage instructions in Swahili and confirm the patient understood, at a rural clinic with no signal.
- A student needs to translate study material between English and Swahili on a laptop that is often offline.
- A traveler at a border needs quick, private translation they are not willing to send to a server.

### 1.4 Personas

- **Amina, 34, market vendor, Mombasa.** Swahili-first, smartphone is her only computer, pays per megabyte. Needs speech in, speech or text out, instant, free.
- **Brian, 28, community health worker, Kisumu.** Needs accurate phrase-level translation in both directions, in a noisy environment, offline.
- **Zawadi, 19, student, Nairobi.** Laptop with intermittent wifi, needs text translation for study, privacy-conscious.

### 1.5 Success metrics

- Cold start to first usable screen under a stated budget.
- End of speech to translated text under a stated budget on the demo Mac.
- Zero network calls after initial model download, verified by monitoring.
- Demo completes a clean two-way exchange in one continuous airplane-mode take.

### 1.6 Non-goals (explicitly out of scope for v1)

- More than the English-Swahili pair in the live demo (the model supports 19 languages, which we surface as a roadmap, not a demo risk).
- Swahili speech output (no confirmed Swahili TTS in QVAC, see Part 6).
- Accounts, cloud sync, history stored off-device, payments, or any server component.
- Medical, legal, or financial high-stakes translation guarantees. We state a human-in-the-loop caveat.

## Part 2. Experience and interface design

### 2.1 Design principles

- **One job per screen.** The main screen does translation and nothing else.
- **Voice first, typing always available.** The mic is the hero, but the keyboard is a first-class path, not a fallback afterthought.
- **Offline is a feature, not a warning.** The UI treats "no internet" as the normal, proud state, with a small offline badge, not an error.
- **Honest asymmetry.** Because Swahili output is text-only in v1, the UI makes that clear and calm rather than hiding it.

### 2.2 The single main screen (wireframe in words)

A calm, high-contrast, two-panel layout.

```
+--------------------------------------------------------------+
|  Yako                                    [ offline badge ]   |
|--------------------------------------------------------------|
|  ENGLISH  (source)                 |  SWAHILI  (target)      |
|  [ text / transcript appears   ]   |  [ translation text ]   |
|                                  [ swap <-> ]               |
|--------------------------------------------------------------|
|        ( big round mic button )      [ type instead ]        |
|  status: listening / translating / ready                     |
+--------------------------------------------------------------+
```

- A large central mic button with clear states (idle, listening, processing, speaking).
- A swap control flips source and target languages.
- Source and target panels show the live transcript and the translation, with the target panel also triggering English TTS when Swahili is the source.
- A subtle status line always says what is happening in plain words.

### 2.3 Interaction and motion

- Mic button gives immediate visual and haptic-style feedback (scale, ring pulse) on press, so the user trusts it heard them.
- Transcript streams in token by token, so latency is perceived as progress, not a spinner.
- A gentle pulse on the target panel when the translation lands.
- Motion is minimal and respect `prefers-reduced-motion`.

### 2.4 Visual design system

- **Palette.** High-contrast light theme with a deep indigo primary, a warm accent for the mic, and a soft neutral background. A dark theme follows the same tokens. Colors meet WCAG AA contrast (4.5:1 for text).
- **Type.** A clean system font stack for speed and offline safety (no webfont download). Generous sizes, since the persona may be using a small or shared screen.
- **Spacing and shape.** Roomy touch targets (at least 44 pt), rounded corners, generous whitespace, one accent color doing the work.
- **Iconography.** A simple mic glyph, a swap glyph, a speaker glyph, and an offline glyph. No decorative clutter.

### 2.5 States and empty views

- **First run.** A friendly one-time card that downloads the two models with a progress bar and explains, in one sentence, that everything after this works offline.
- **Listening.** Clear waveform-style indicator and a "tap to stop" affordance.
- **Processing.** A short status message, never a dead spinner.
- **Error.** Plain-language recovery (for example "I didn't catch that. Tap to try again, or type instead.").
- **No translation yet.** An inviting empty state with a hint like "Press the mic and speak, or type below."

### 2.6 Copy and tone

Short, warm, plain sentences. No jargon. Error and status messages read like a helpful person, not a stack trace. Examples are "Listening...", "Translating...", "Here it is in Swahili.", "Try that again."

## Part 3. System architecture

### 3.1 High-level shape

A single local process. Three layers.

```
+-------------------------------------------------------------+
| Presentation layer     UI shell (single screen, state machine)|
+-------------------------------------------------------------+
| Orchestration layer    pipeline controller, state machine,  |
|                        model lifecycle, error mapping        |
+-------------------------------------------------------------+
| Capability layer (QVAC)                                      |
|   Whisper transcription -> AfriSLM translation -> TTS speech |
+-------------------------------------------------------------+
```

### 3.2 The pipeline, step by step

1. **Capture.** Microphone (or keyboard) feeds the orchestrator. Mic input runs through Silero VAD to detect clean end-of-speech.
2. **Transcribe.** Whisper (tiny or base) converts speech to text in the source language. We filter known Whisper hallucinations (repeated tokens, phantom phrases on silence).
3. **Translate.** AfriSLM-0.8B-Q4_K_M receives the transcript with the exact model-card prompt template (system "professional {src} to {tgt} translator", user "Please translate the following {src} text into {tgt}: {text}.").
4. **Render.** The translation renders as text in the target panel. If the target is English, the TTS engine speaks it. If the target is Swahili, text is shown (speech is a stretch goal).
5. **Loop.** The swap control flips direction for the next turn of the conversation.

### 3.3 Module breakdown

- **`app/`** UI shell, screens, components, design tokens.
- **`pipeline/`** orchestration, the translation state machine, error mapping.
- **`models/`** model download, integrity check, `assessModelFit()`, load, unload, memory management.
- **`audio/`** mic capture, VAD, playback, mic-gating during TTS.
- **`config/`** language registry, model registry, feature flags.
- **`observability/`** local-only metrics and structured logs (see Part 10).
- **`tests/`** unit, integration, golden, and offline-verification tests.

### 3.4 State machine

The pipeline is a small, explicit state machine, which keeps the UI honest and testable.

```
idle -> listening -> transcribing -> translating -> rendering -> speaking -> idle
  \_________________________________ error ________________________________/
```

Every transition is a named event. The UI renders purely from state. This is the single most important code-quality decision in the app, because it makes the whole flow deterministic and reviewable.

### 3.5 Model registry and lifecycle

- Models are declared in one config file with name, file, size, checksum, and role (transcription, translation, tts).
- On first run, the orchestrator calls `assessModelFit()`, downloads with resumable progress, verifies integrity, and loads.
- Models are loaded lazily and can be unloaded to reclaim memory, important on 16 GB.
- The registry makes it trivial to swap Whisper tiny for base, or AfriSLM 0.8B for a different size, without touching pipeline code.

### 3.6 Technology choices (locked)

- **QVAC JS SDK** (`@qvac/sdk`) as the only AI runtime. Addons: `@qvac/transcription-whispercpp`, `@qvac/translation-nmtcpp` or the LLM translation addon for the GGUF model, `@qvac/tts-ggml`.
- **App shell.** A thin desktop shell over the JS SDK, with an Expo path preserved for Android. The UI logic is platform-agnostic so the same code runs on Android later.
- **Language.** TypeScript everywhere, strict mode, for the reliability a judge reading the code expects.

## Part 5. Code quality and engineering standards

This is where "top 5 company" discipline shows up in the diff.

- **TypeScript strict.** No `any` without a justification comment. Shared types for pipeline events, model handles, and state.
- **Formatting and linting.** Prettier and ESLint with a strict, standard config, enforced by a pre-commit hook. One command (`npm run check`) runs typecheck, lint, and format verification.
- **Conventional commits.** Imperative, scoped messages (for example `feat(pipeline): add translation state machine`). The git history reads like a changelog.
- **Small, reviewable modules.** Each module in Part 3.3 has one job and a narrow public interface. Orchestration never reaches into QVAC internals. It goes through the capability layer.
- **Error taxonomy.** A small set of typed errors (MicError, TranscribeError, TranslateError, TtsError, ModelError) each mapped to a plain-language user message. No raw exceptions reach the UI.
- **Configuration over constants.** Model names, sizes, thresholds, and paths live in config, never scattered as magic strings.
- **No secrets, ever.** There are no API keys in this design, and a secret-scanning step (for example gitleaks) runs in checks to prove it.
- **Dependency discipline.** Minimal, well-known dependencies, pinned, with an audit step (`npm audit`) in checks.
- **License and attribution.** A NOTICE or credits section naming QVAC, TranslatePsy-AfriSLM (Apache 2.0 model), and whisper.cpp, satisfying the hackathon disclosure rule.

## Part 6. The AI and ML layer

### 6.1 Models and roles

| Role | Model | Size / format | Why |
|---|---|---|---|
| Transcription | Whisper tiny (base as an option) | whisper.cpp `.bin` | Covers English and Swahili, small, fast on CPU/Metal |
| Translation | TranslatePsy-AfriSLM-0.8B | GGUF Q4_K_M | Best quality per MB, supports the pair, fits 16 GB |
| Speech out | QVAC TTS (Supertonic, English) | `modelType:"tts"` | English voice output, local |
| VAD | Silero | GGML | Clean end-of-speech detection |

### 6.2 Prompt and parameter discipline

- The AfriSLM prompt template is reproduced exactly from the model card and stored as a versioned constant, with the source and target language names written out in words (English, Swahili).
- Generation parameters (context size, temperature, max tokens) are tuned for short, faithful translation, not creativity, and recorded in config.
- A note documents the known AfriSLM limitations (synthetic training data, weaker on dialect, not for high-stakes) so the submission is honest.

### 6.3 Robustness of the pipeline

- **Hallucination filtering** on Whisper output (silence-induced phantom text, repetition loops).
- **Mic gating** during TTS playback so the app does not transcribe its own voice.
- **Empty and noisy input** handled gracefully with a friendly retry path.
- **Direction integrity.** The swap control reliably re-points the prompt template, verified by tests.

## Part 7. Performance and resource engineering

### 7.1 Budgets (we measure and publish against these)

- Cold start to interactive screen.
- End of speech to translated text.
- Text to spoken audio.
- Peak resident memory during a full exchange.

### 7.2 How we stay within budget

- Choose the 0.8B Q4_K_M translation model and Whisper tiny as defaults.
- Run `assessModelFit()` before loading.
- Load models lazily and unload on demand.
- Stream transcription and translation so the user sees progress instead of waiting on a single blocking call.
- Close other heavy apps during the recorded demo.

### 7.3 What we publish

A small "About this build" panel and a README table with the measured numbers and the exact hardware (Mac, arm64, 16 GB, macOS 27), plus the documented Android target. Judges love reproducible numbers.

## Part 8. Privacy, security, and trust

Privacy is the product's headline feature, so it is engineered, not asserted.

- **Local by construction.** No AI feature touches the network. The only network use is the one-time model download, stated plainly in the UI and the submission.
- **Offline proof.** A pre-demo check disables wifi and confirms the full loop still runs. This is also a test (see Part 9).
- **Data handling.** Transcripts and translations live in memory for the session. If any history is kept, it is on-device only, with a one-tap clear. Nothing is uploaded.
- **Threat model (short).** The main risks are a tampered model file and a malicious dependency. Countermeasures are model integrity checks, pinned dependencies, secret scanning, and `npm audit`.
- **Permissions.** The app requests only microphone access, and explains why in plain language at first use.
- **No secrets in repo.** Enforced by the secret-scanning check and the SECURITY.md policy already in the repo.

## Part 9. Testing and quality assurance

A hackathon timeline does not excuse a fragile demo. We test the riskiest things hardest.

- **Unit tests.** The state machine transitions, error mapping, prompt-template construction, and the language swap logic.
- **Integration tests.** A scripted English phrase to Swahili text, and a scripted Swahili phrase to English text, run offline against the real models.
- **Golden tests.** A small set of fixed input phrases with expected translation shape (not exact-match, since models vary, but language detection and key-content checks), so a regression is caught immediately.
- **Offline-verification test.** The full exchange runs with networking disabled. This test doubles as our demo-readiness check.
- **Audio path test.** Mic capture to transcription to playback, on the real machine, including mic-gating during TTS.
- **Performance test.** A timed run that records cold start, speech-to-text, and text-to-speech numbers into the About panel.
- **A recorded "known good" demo script.** The exact phrases used in the video, rehearsed so the live take is reliable.

## Part 10. Observability and debugging (local only)

- **Structured local logs.** Named pipeline events with timestamps and durations, written locally, never transmitted. These give us the latency numbers and make demo-day debugging fast.
- **A diagnostics view.** A hidden panel showing model status, memory, and the last pipeline timings, useful for the About screen and for a judge who wants to peek under the hood.
- **Crash discipline.** Any failure lands in the typed error taxonomy and produces a plain-language message plus a local log line.

## Part 11. Accessibility and inclusive design

- **Contrast and type.** WCAG AA text contrast and large, legible type.
- **Reduced motion.** Honors `prefers-reduced-motion`.
- **Keyboard and screen reader.** The whole flow is operable by keyboard, with labeled controls and live-region announcements for the transcript and translation, so a screen reader user gets the same conversation.
- **Touch targets.** At least 44 pt throughout.
- **Plain language.** All copy at a low reading level, which also helps the Swahili-first persona.

## Part 12. Internationalization and localization

- **The product is inherently multilingual.** Source and target are user-facing language choices backed by the AfriSLM registry, with English and Swahili as the demoed pair.
- **UI strings** are externalized into a strings file from day one, so the shell can be localized (for example a Swahili UI) without code changes.
- **Language names** are written out in full words for the AfriSLM prompt template and displayed consistently in the UI.
- **Number, date, and direction** handling uses locale-aware formatting, and the layout tolerates longer translated strings without breaking.

---

## Part 13. Offline architecture and networking policy

- **One network moment.** The first-run model download. Everything else is offline, always.
- **Resumable downloads** with visible progress and a retry that picks up where it stopped.
- **Integrity checks** on downloaded models before first load.
- **A stated network-feature list** for the submission, exactly one line. Model download uses the network once, and every AI feature then runs fully offline.

## Part 22. Open decisions to confirm before Day 1

1. **App shell.** Thin desktop shell versus Expo-first. Recommendation is a thin desktop shell for the demo with the Expo path preserved, to be confirmed at scaffold time based on the fastest route to a stable offline run.
2. **Whisper tiny versus base.** Start with tiny for speed, promote to base if accuracy on the real mic is unacceptable.
3. **TTS engine.** Supertonic (English) as the default, validated during Day 2 audio work.
4. **UI framework detail.** Final choice inside the shell, optimized for a single, fast, accessible screen.
